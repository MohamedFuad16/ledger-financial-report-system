# Annual Report → asset-side balance sheet

LLM extraction of the asset side of a balance sheet from an Annual Report PDF,
into a fixed 27-row schema, with an accuracy benchmark against stored golden
answers.

The assignment input is 3M's FY2022 Annual Report, but the system is built to
take any company's Annual Report: nothing in the schema, prompt or pipeline is
specific to 3M, and the answer keys are used only for scoring, never as input to
the model.

## Layout

| Path | What it is |
|---|---|
| `models.py` | **The output contract.** Pydantic models every strategy must satisfy. Validates only — it never repairs, maps or scores. |
| `reconcile.py` | Deterministic arithmetic verification: do the model's own subtotals add up? Needs no answer key, and never changes a value. |
| `normalize.py` | Repair layer: turns a nearly-valid LLM reply into a valid one, and reports every change it made. |
| `ratelimit.py` | Adaptive concurrency + HTTP 429 backoff, measured from real responses. |
| `schema.py` | The fixed 27-row target schema, and the golden answers used for scoring. |
| `extraction.py` | PDF → text, one function per strategy, plus text-health checks. |
| `prompts.py` | System prompt + user-prompt assembly. Its output contract is generated from `models.py`. |
| `pipeline.py` | One extraction end to end: convert → prompt → call → validate → score → persist. |
| `api_client.py` | Provider HTTP calls and deterministic reply parsing. |
| `server.py` | Flask API. Routes only; all work goes through `pipeline.py`. |
| `corpus/` | Firecrawl discovery, direct PDF download, document screening and atomic manifest storage. |
| `corpus_worker.py` | Standalone background corpus-job entry point for CSV/JSON company lists. |
| `frontend/` | The React/Vite web UI. `frontend/dist/` is served by Flask. |
| `static/` | Archived pre-React UI source; no longer served. |
| `app.py` | Legacy Streamlit UI, now a thin wrapper over the same pipeline. |
| `test_contract.py` | Offline checks — no API key, no network. |
| `test_dataset/` | Evaluation PDFs, FY2020–FY2025. See its own README. |
| `ROADMAP.md` | What is planned next, including the Firecrawl-based large-scale corpus. |
| `runs/` | New company/FY/timestamp namespaced run artifacts; legacy strategy folders remain readable. |
| `uploads/` | New company/year/timestamp namespaced uploaded PDFs (gitignored); historical flat uploads are preserved. |

The dashboard's main chart plots **parse time against exact accuracy** in four
quadrants on a log-scaled x axis. Every run record names the parser that
produced it, so a Strategy 2 run is identifiable as PyMuPDF4LLM / Docling /
pdf-inspector rather than just "Strategy 2".

## Strategies

Both strategies send the whole report in one request. Only the **document
representation** differs — that is the variable under test.

| | Strategy 1 | Strategy 2 |
|---|---|---|
| Converter | PyPDF `extract_text()` | PyMuPDF4LLM markdown |
| Tables | flattened, columns may interleave | structure preserved |
| Page markers | yes | yes (`page_chunks=True`) |
| Everything else | identical | identical |

Neither strategy uses OCR, page selection, chunking, retrieval, reranking, or
the answer key. Those belong to later strategies, if they are added.

### The contract is shared, and it only validates

Two separate steps, on purpose:

```
model reply → normalize.normalize_payload() → models.validate_extraction() → pipeline.compute_metrics()
              repair representation,           check fields & types             score vs. golden answers
              report every change              (Pydantic)
```

`models.py` answers one question: *does this reply have the required fields, in
the required shape, with the required types?* It checks that all 27 rows are
present, in schema order, named exactly as the schema names them, that
`answer_m_usd` is a JSON number or null, that `confidence` is a number in
`[0, 1]`, and that `detected_fiscal_year` is a 4-digit string. It does not
rename, reorder, parse `"1,234"`, compute a subtotal, or compare anything to an
answer key. A contract violation is therefore always a real one.

`normalize.py` is the repair layer that runs *before* it — parsing `"$1,234"`
and `"(16,820)"`, folding `92` / `"95%"` into `0.92` / `0.95`, mapping
`"Cash and Cash Equivalents"` onto `"Cash & Cash Equivalents"`, sorting rows
back into schema order. Every repair is recorded in `prediction.json` under
`contract_repairs`, so nothing is fixed silently. Anything it cannot repair is
left untouched and the contract rejects it.

The prompt's `OUTPUT CONTRACT` block is generated by `models.output_contract_text()`,
so the instructions the model receives cannot drift from what is enforced.

### Concurrency and rate limits

Z.AI does not publish RPM/TPM numbers — its
[usage policy](https://docs.z.ai/devpack/usage-policy) says limits are adjusted
dynamically by plan tier and load. So nothing is hardcoded:

- `POST /api/uploads` stages the PDFs once and returns a **pre-flight plan** —
  page counts, estimated input tokens (sampled, ~5% low on this corpus) and a
  recommended concurrency — before any paid call is made.
- `ratelimit.AdaptiveLimiter` caps in-flight requests. On an HTTP 429 it halves
  the permitted concurrency, waits the provider's `Retry-After` (or an
  exponential backoff with jitter), retries, and restores one permit at a time
  after sustained success.
- Any `x-ratelimit-*` headers the provider does return are recorded and served
  from `GET /api/ratelimit`, labelled as measured rather than documented.

The global request ceiling and Firecrawl key live in Settings. Individual
strategy pages do not carry independent rate sliders, so every batch shares the
same measured limiter state.

### Annual Report corpus

The **Report corpus** page discovers official Annual Reports for FY2020–FY2025.
Firecrawl map/search calls identify candidate URLs; PDFs are downloaded directly,
validated as PDFs, hashed, screened for fiscal year/balance-sheet/text health,
and written as:

`corpus_dataset/<company>/<year>/<downloaded_at>/<company>_annual_report_<year>.pdf`

The manifest is `corpus_dataset/corpus_manifest.json`. Corpus downloads are
never passed to the LLM automatically. A long job can also be run independently
of a browser tab:

```bash
.venv/bin/python corpus_worker.py research/bakuraku/customers.csv --years 2020 2021 2022 2023 2024 2025
```

### Live execution

`POST /api/extract/stream` runs one or more staged PDFs concurrently and streams
Server-Sent Events — one per pipeline step, per file. The UI renders a track per
file (Save → Extract → Prompt → Model → Contract → Output) with the in-flight
step animated, so concurrent work looks concurrent and a rate-limit backoff is
visible as it happens.

Note on parallelism: the model call is I/O and parallelizes well. PyPDF text
extraction is pure Python and is serialized by the GIL, so Strategy 1's
extraction phase does not speed up with concurrency; PyMuPDF releases the GIL
for much of its work, so Strategy 2's does.

## Providers, reasoning and prompt caching

The client speaks the OpenAI chat-completions shape, so any compatible endpoint
works. Providers are declared in `providers.py`; adding one is a data change,
not a client change.

| Provider | Reasoning parameter | Automatic prompt caching | Default model |
|---|---|---|---|
| **OpenRouter** (default) | `reasoning: {effort}` | yes | `deepseek/deepseek-v4-flash-latest` |
| OpenAI | `reasoning: {effort}` | yes | `gpt-5.6-sol` |
| Z.AI / Z.AI Coding | `thinking: {type}` | no | `glm-5.3` |
| Custom | `reasoning: {effort}` | — | — |

**Reasoning effort** is a single provider-neutral setting —
`none · minimal · low · medium · high · xhigh · max` — translated per provider.
`none` disables reasoning; Z.AI, which only has on/off, collapses every non-`none`
level to on. It can be set as a default in Settings and overridden per run.

**Prompt caching is prefix-based**, so prompt order is load-bearing for cost.
The system prompt and the 27-row `TARGET_SCHEMA` are byte-identical on every
request and are sent *first*; the fiscal-year hint, the parser's document map and
the report text follow. That makes a **~2,660-token cacheable prefix** — above
OpenAI's 1,024-token minimum, and cached automatically by DeepSeek and OpenAI.
An earlier version put the schema after variable content, which made it
uncacheable on every call.

Cache accounting is read from `usage.prompt_tokens_details` (`cached_tokens`,
`cache_write_tokens`) and stored on each run as `usage`, with `cache_hit_rate`
and, where the provider reports it, `cost_usd`.

Settings are stored in `.env` as `LLM_PROVIDER` / `LLM_API_KEY` / `LLM_MODEL` /
`LLM_BASE_URL` / `LLM_REASONING_EFFORT` / `LLM_TEMPERATURE`. The older `GLM_*`
names are still read, so an existing setup keeps working.

## Scoring

`accuracy` — exact matches over the schema items the golden set defines. A value
counts only if the model also reported confidence ≥ 0.8; a low-confidence guess
is not an answer. `null` never counts as a match for a golden `0`.

`coverage` — share of the 27 rows answered with confidence ≥ 0.8.

FY2025 uses its explicitly partial 19-row key; accuracy is scored over only
those defined rows and never against invented values or another year.

The identical rule runs in `pipeline.compute_metrics` (server) and
`calculateAccuracy` (UI), and is covered by `test_contract.py`.

## How a prediction is checked, end to end

The same five stages run for **every strategy** — S1, every S2 parser variant,
and anything added later — because they all go through `pipeline.run_pipeline`.

```
GLM reply (JSON: 27 rows, each with answer_m_usd + confidence)
   │
   ├─ 1. normalize.py            repair representation      "1,234" → 1234, reorder rows
   │                                                        (reports every repair; fixes nothing else)
   ├─ 2. models.py               the Pydantic contract      27 rows? right names? right types?
   │                                                        (rejects, never repairs)
   ├─ 3. apply_confidence_gate   the 0.8 rule               confidence < 0.8 → accepted = false
   ├─ 4. reconcile.py            deterministic arithmetic   do the accepted values add up?
   │                                                        (reports, never repairs)
   └─ 5. compute_metrics         scoring                    compare accepted values to the answer key
```

**Stage 3 is where "below 0.8 means no answer" happens**, and it runs *after* the
contract, not before. The raw `answer_m_usd` is kept and an `accepted` flag is
stamped alongside it, rather than the value being overwritten with null. That
choice is deliberate: the number the model produced is evidence, and preserving
it is what made it possible to re-score all 48 historical runs when the
threshold moved from 0.5 to 0.8. Overwriting would have destroyed that. Every
consumer — the tables, the charts, the CSV export, reconciliation and scoring —
reads `accepted`, so a sub-threshold row displays as `—` and counts as
unanswered everywhere.

**Stage 4 answers the "do the 27 rows add up?" question.** It checks the seven
identities the schema implies:

```
Quick Assets                    = Cash + Accounts Receivable + Other Quick
Other Current Assets (subtotal) = Marketable Securities + Short-term Loan + Advance Payments + Other Current
Current Assets                  = Quick Assets + Inventories + Other Current Assets (subtotal)
Tangible Assets                 = Land + Buildings + Plant & Machinery + CIP + Other Equipment + Accum. Depreciation
Financial Assets                = Investments + Long-term Loan + Other Financial Assets
Fixed Assets                    = Tangible + Intangible + Financial + Other Fixed
Total Assets                    = Current Assets + Fixed Assets + Deferred Charges
```

It uses the **accepted** values, not the raw ones — a figure the rest of the
system refuses to count must not silently prop up a subtotal. An identity that
needs a rejected or null value is reported as *skipped*, not as passing.

**Stage 5 is exact accuracy, and it is a straight per-row comparison.** For each
row: if `accepted`, compare `answer_m_usd` to `GOLDEN_ANSWERS_STORE[fy][item]`
within 0.5 (values are in millions). Accuracy is the share of the rows the
answer key defines that match exactly. Nothing is summed, inferred, or
substituted at this stage — reconciliation deliberately does not feed it,
because "repairing" a mismatch means guessing which side is wrong, and a wrong
guess corrupts the measurement the benchmark exists to produce. Re-asking the
model about failed identities is Strategy 4's job.

### What reconciliation is, and is not, worth

Measured across 48 scored runs:

| | n | Mean accuracy |
|---|---:|---:|
| All seven identities hold | 47 | 72.1% |
| At least one identity fails | 1 | 74.1% |

**47 of 48 runs are perfectly self-consistent while averaging 72% accuracy.**
Reconciliation catches arithmetic slips, but it cannot catch the dominant error
in this task, because a misclassification stays consistent: when the model puts
1,563 in Other Fixed Assets instead of Other Financial Assets, both subtotals
still sum to the printed 4,271.

So it is a genuine but *weak* signal on its own. Its value is that it needs no
answer key, which matters when the corpus grows to companies that have none —
but it must not be mistaken for a proxy for accuracy.

## Confidence threshold: 0.8, and why

A row only counts as *answered* when the model's own confidence is at or above
`CONFIDENCE_THRESHOLD`. That was 0.5; it is now **0.8**, chosen from measurement
rather than taste. Across 824 scored (row, run) observations:

| Model's confidence | n | Actually correct |
|---|---:|---:|
| < 0.50 | 104 | 2.9% |
| 0.50 – 0.70 | 91 | 60.4% |
| 0.70 – 0.80 | 88 | 58.0% |
| **0.80 – 0.90** | 160 | **93.8%** |
| 0.90 – 0.95 | 78 | 100% |
| ≥ 0.95 | 303 | 100% |

There is a cliff at exactly 0.80. Below it the model is right ~59% of the time —
a coin flip counted as an answer. Accepting at 0.5 gave 720 accepted answers of
which 83 were wrong (88.5% precision); accepting at 0.8 gives 541 of which 10
are wrong (**98.2% precision**).

This makes the headline accuracy numbers *lower* than earlier sections report,
because a correct-but-unconfident row is now a miss. That is the intended
meaning: "right and sure" rather than "right, possibly by luck".

Three numbers are now reported, because they answer different questions:

- **Coverage** — of 27 rows, how many did the model commit to?
- **Exact accuracy** — of the rows the answer key defines, how many are exactly right?
- **Precision** — of the rows it committed to, how many are right? *Can I trust a confident answer?*

Six documents × four extraction technologies, one GLM call each, `glm-5.3`,
temperature 0.1, reasoning on, concurrency 3. 28 runs, zero rate-limit events.

| FY2023 | 70.4% | 66.7% | 70.4% | **74.1%** |

| **Mean (excl. FY2021)** | 68.7% | 69.1% | 66.6% | **71.4%** |

|---|---:|---:|---:|---:|---:|

| **pdf-inspector** | **0.4s** | 125,096 | +1.7% | 139s | **139s** |

¹ FY2021 has a broken text layer; no text-based extractor can read its balance
sheet. ² FY2025 is scored against a 19-row partial key.

### Verdict: pdf-inspector, with PyPDF as the fallback

**pdf-inspector wins on every axis that matters and loses on none.** Best mean
accuracy (71.4%), best coverage (71.1%), fastest extraction by a wide margin
(0.4s — 6× faster than PyPDF, 50× faster than PyMuPDF4LLM, 270× faster than
Docling), and near-zero token overhead (+1.7%). It also classifies the document
(text_based / scanned / image_based / mixed) up front, which is exactly the
signal needed to reject unusable PDFs at scale.

**Docling is the clear loser here**: lowest accuracy (66.6%), lowest precision
(94.9%), 38% more tokens, and 108s per document — 270× the extraction cost for a
worse result. Its ML layout model is solving a problem these documents do not
have.

**Caveat, stated plainly:** the accuracy spread across the four (66.6–71.4%) is
about 5 points, and the same technology on the same file has previously swung
7.4 points between identical runs. **At n=1 per cell, the accuracy ranking is
not statistically meaningful.** What *is* meaningful, because it is deterministic
and not sampled, is speed and token cost — and there pdf-inspector wins
decisively. Choose it for those, not for the accuracy number.

## Where the accuracy actually goes

Per-item failure counts across all stored runs (excluding the FY2021 document
failure) split cleanly into four issues:

**1. Mapping convention, not extraction — the dominant cost.**
The model reads the numbers correctly and files them in the wrong row.

The three rows that fail in almost every run are one disagreement about which
bucket an item belongs in. FY2022 Note 7 "Other assets" totals 4,271, and both
the answer key and the model account for all 4,271 — differently:

| | Answer key | Model |
|---|---:|---:|
| Investments | 81 + 886 = **967** | 81 + 886 = **967** ✓ |
| Other Financial Assets | 1,225 + 265 + 73 = **1,563** | 265 = **265** |
| Other Fixed Assets | 959 + 782 = **1,741** | 959 + 1,225 + 73 + 782 = **3,039** |
| Financial Assets | **2,530** | **1,232** |

Every figure is read correctly, the arithmetic is right, the citation is right
(Note 7, page 76). The key treats prepaid pension and insurance receivables as
*financial* assets; the model treats them as *other* assets. That is an
accounting-policy convention, invisible in the PDF, and no parser can supply it.

| Row | Wrong in | What happens |
|---|---|---|
| Other Equipment | every run | operating-lease right-of-use assets are dropped, so Tangible Assets is short by exactly that amount |
| Tangible Assets | every run | consequence of the above: reported as PP&E-net |
| Other Financial Assets / Financial Assets / Other Fixed Assets | almost every run | the single "Other assets" line is not split using its note |
| Advance Payments / Other Current Assets | every run | prepaid expenses are filed as advance payments |
| Intangible Assets | 3 runs | goodwill omitted, only "intangible assets, net" reported |

*Outlook:* largely addressed — the mapping rules now spell out the ROU, goodwill,
"other assets"-split and prepaid-vs-advance distinctions, and accuracy moved to
88.9%. The residual 3 of 27 are the remaining "other assets" split rows. A
post-hoc reconciliation pass (check each subtotal against its components and
against the printed total, then re-ask only for the rows that do not reconcile)
is the natural next strategy and would catch those mechanically rather than by
prompt wording.

**2. Null vs. zero — a spec conflict, ~5 rows.**
Short-term Loan, Long-term Loan, Other Quick Assets, Deferred Charges and
Advance Payments are `0` in the answer key, but the original prompt said *"do not
assume 'not found' means zero"* — so the model returned `null` and lost the row.
The prompt now distinguishes a row that decomposes a stated subtotal (absent
component → `0`) from a standalone row that cannot be established (→ `null`).
That is worth up to 18.5% of the score on its own.

*Outlook:* solved. Post-fix runs answer all five rows and reach 100% coverage.

**3. Unreadable input — FY2021, 1/27.**
Not a model failure. The FY2021 PDF's financial-statement pages use subset fonts
with no `ToUnicode` mapping, so 71 of 142 pages extract as glyph ids. The
mapping is not recoverable from the file (no `cmap`, no `post` table). The
pipeline now detects this and warns instead of sending glyph soup to the model.

*Outlook:* requires OCR or a vision model over rendered pages. Detection is in
place so the failure is visible and attributed correctly rather than being
counted as a bad model answer.

**4. Subtotal arithmetic.**
Fixed Assets was wrong in 3 runs, always as a consequence of a wrong component
rather than an arithmetic slip. Total Assets was correct in *every* run — the
model reads the printed total reliably.

*Outlook:* fixing the component rows fixes these; the reconciliation pass in (1)
would also surface them automatically.

## Local artifacts

```text
runs/<S1|S2>_<timestamp>_<n>/
├── request.json        # exact payload sent (no API key, no auth header)
├── raw_response.json   # provider reply verbatim, or the error
└── prediction.json     # validated rows + metrics + warnings
```

Run ids and upload filenames carry a counter as well as a timestamp, so a
concurrent batch cannot make two runs share one directory.

## Security note

This is a local experiment UI, not a production secret-management system. The
API key is stored as plaintext in the project's local `.env` after successful
verification. Do not commit or share `.env`.


## What's next

Strategies 3 (hybrid retrieval) and 4 (agentic reconciliation) are not built.
The residual-error table above says the next strategy should be a
reconciliation/repair pass, not another parser.

After all four strategies are verified on this 6-document set, the plan is to
scale the corpus to ~100 companies using Firecrawl, so accuracy is measured
across filers rather than against 3M's house style. The full spec — discovery
call order, corpus manifest, the ground-truth-at-scale problem, and measured
cost estimates — is in **[ROADMAP.md](ROADMAP.md)**.

Firecrawl is already registered as an MCP server (`firecrawl`) and
`FIRECRAWL_API_KEY` lives in the gitignored `.env`. Nothing in the extraction
pipeline touches the network; the corpus builder will be a separate `corpus/`
package.
